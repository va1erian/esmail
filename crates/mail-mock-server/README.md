# mail-mock-server

An in-process IMAP + SMTP server, internal to this workspace, that exists
only to let esmail's real network code (`crates/esmail/src/imap.rs`,
`crates/esmail/src/smtp.rs`) be tested against *something* rather than
nothing. Nothing about esmail itself changes to accommodate it.

## Why a hand-rolled server instead of a real one (e.g. GreenMail)

`imap.rs` always speaks implicit TLS (`TlsConnector::builder().build()`,
default certificate validation, no way to disable it) — that's real client
code we don't want to weaken just to make it testable. A real IMAP test
server (GreenMail, Dovecot, ...) either doesn't present a certificate at all
by default, or presents one whose trust configuration is awkward to pin down
reliably across CI images. Rolling a small server here means:

- We control exactly which TLS identity it presents (`certs/server.crt`,
  signed by `certs/ca.crt`, both committed and regenerable via
  `certs/regen.sh`), so trusting it is one well-understood step: install
  `ca.crt` as an extra trusted root.
- We only need to implement the exact slice of IMAP4rev1 esmail's client
  actually sends (`LOGIN`, `AUTHENTICATE XOAUTH2` and SMTP `AUTH XOAUTH2`
  against per-user tokens from `Store::add_oauth_token`, `LIST`, `EXAMINE`, `FETCH (UID ENVELOPE)`,
  `UID FETCH ... RFC822`, `LOGOUT`) and verified, response-by-response,
  against the vendored `imap-proto`/`async-imap` grammar rather than hoping
  a full third-party server's edge cases line up.
- SMTP delivery writes straight into the same in-memory mailbox store the
  IMAP server reads from, so a send-then-fetch round trip is just two
  requests against one process — no external server to keep in sync.

The trade-off: this is not a general-purpose IMAP/SMTP server. It has no
`SEARCH`, `IDLE`, `APPEND`, flags, or multi-user isolation beyond one test
account. If esmail's client grows to use more of the protocol, this server
needs matching additions — see `imap_server.rs`'s and `smtp_server.rs`'s doc
comments for exactly what's implemented.

## Trusting the test CA

The bundled certificate (`certs/ca.crt`) is a throwaway, 10-year, test-only
root generated by `certs/regen.sh` — it authenticates nothing real and its
private key was never even kept (see the script). Tests that connect over
TLS (`crates/mail-mock-server/tests/smoke.rs`, and esmail's own
`crates/esmail/tests/imap_smtp_integration.rs`) need it trusted by the OS,
because `native-tls`'s default certificate validation reads the OS trust
store and neither of those client crates has a way to point it at a custom
root without changing esmail's own connection code.

**CI (Linux, `ubuntu-latest`)** does this automatically as a job step
before running the tests — see `.github/workflows/ci.yml`'s `test-linux`
job. `native-tls` uses OpenSSL there, which reads the system trust store,
so `update-ca-certificates` is all it takes. No developer action needed for
CI runs.

**Local runs** need the same trust established once, and it's OS-specific:

- **Linux**: `sudo cp certs/ca.crt /usr/local/share/ca-certificates/esmail-test-ca.crt && sudo update-ca-certificates`
- **Windows** (what this repo actually runs on): `native-tls` uses Schannel,
  which reads the Windows certificate store, not `SSL_CERT_FILE` or any
  other env var. Per-user (no admin needed):
  ```bash
  certutil -user -addstore -f "Root" crates/mail-mock-server/certs/ca.crt
  ```
  This *was run once already* in this worktree's setup, with the user's
  explicit go-ahead after asking first (installing a trusted root is a
  security-relevant change; it should never happen silently). It only
  trusts the throwaway `esmail-test-ca` — nothing else — and only for the
  current Windows user account. **To remove it:**
  ```bash
  certutil -user -delstore Root esmail-test-ca
  ```
- **macOS**: `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain crates/mail-mock-server/certs/ca.crt`

Tests that need the trust gate on the `ESMAIL_TEST_CA_TRUSTED=1` env var
(rather than failing confusingly on a machine that hasn't done this) — set
it once you've trusted the CA:

```bash
ESMAIL_TEST_CA_TRUSTED=1 cargo test -p mail-mock-server --test smoke
ESMAIL_TEST_CA_TRUSTED=1 cargo test -p esmail -- --ignored
```

SMTP needs no TLS trust at all: esmail's `TlsMode::None` (its doc comment
already flags this mode as existing "for a local/test server") sends
plaintext, and `smtp_server.rs` only ever speaks plaintext SMTP.

## Running it standalone (Docker)

```bash
docker compose up mail-mock-server
```

exposes IMAP (implicit TLS) on `localhost:1993` and SMTP (plaintext) on
`localhost:1025`, seeded with a test account
(`alice@example.com` / `hunter2`, see `src/fixtures.rs`). Point esmail's
login screen at `localhost`, port `1993`, TLS "SSL/implicit" for IMAP, and
`localhost` port `1025`, TLS "None" for SMTP, to exercise the real GUI
against it manually. The container also writes its CA certificate to
`./tmp/mail-mock-server-ca/ca.crt` on the host (via `docker-compose.yml`'s
volume mount and the `CA_OUT` env var) so it's easy to find if you want to
trust it for a manual TLS-aware client too -- see "Trusting the test CA"
above; it's the same certificate as the committed `certs/ca.crt`, just
written out at container startup for convenience.

## Stress / integration tests

`crates/esmail/tests/imap_smtp_integration.rs` drives esmail's actual
`ImapActor`/`SmtpActor` (the same command/event mpsc channels `main.rs`
uses) against this server — pagination, HTML rendering, `cid:` resolution,
attachment extraction, a send-then-fetch round trip, and (under `--ignored`,
since they seed hundreds of messages and take real wall-clock time)
concurrent-load stress tests. Run them with the CA trusted as above, then:

```bash
cargo test -p esmail --test imap_smtp_integration -- --ignored
```
